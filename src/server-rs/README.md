# Mail server (Rust)

The Mail backend in Rust: the HTTP API, the IMAP server and the SMTP server,
over the same PostgreSQL database as the Bun server in `src/server`.

It is built to be swapped for the Bun server without anything else noticing:
the same environment variables (`.env.example`), ports, database schema,
session cookies, password digests and attachment directory. One black-box
suite, `e2e/`, runs unchanged against both servers and is what "the same"
means here.

## Run

```bash
cargo run --release --manifest-path src/server-rs/Cargo.toml
```

It reads the environment the Bun server reads. Two things differ:

- `CLIENT_DIR` — where the built web client is (`bun run build-client`).
  Defaults to `./build/client` under the working directory.
- Attachments are stored in `./attachments` under the working directory,
  as they are for the Bun server.

## Test

```bash
cargo test --manifest-path src/server-rs/Cargo.toml   # unit tests
bun run test:e2e:rust                                 # black-box suite, Rust
bun run test:e2e                                      # the same suite, both servers
```

See `e2e/README.md` for what the black-box suite needs.

## Layout

The module tree follows `src/server/lib`, file for file where that makes
sense, so a change to one server is easy to find in the other.

| Module | What it holds |
| --- | --- |
| `http/` | Request pipeline, sessions, rate limits, uploads, static files, every `/api` route |
| `imap/` | IMAP server: parsers, session state, mailbox and message operations |
| `smtp/` | SMTP server: inbound delivery and authenticated submission |
| `mails/` | Storing, listing, searching, threading and sending mail |
| `mime/` | MIME parser |
| `spam/` | Rules, per-user classifier, DNS blocklists |
| `sso/`, `auth_client.rs` | Optional OpenID Connect sign-in |
| `postgres/` | Pool, boot-time schema work, repositories |
| `js.rs` | JavaScript built-ins the wire format depends on |

## Schema

`schema.json` is the DDL the Bun server issues at boot, generated by
`bun scripts/schema-snapshot.ts`. This crate embeds it, so both servers create
the same tables and agree on the `schema_meta` hashes. A unit test in
`scripts/schema-snapshot.test.ts` fails when the snapshot is stale; regenerate
it whenever a table definition in `src/server/lib/postgres/models` changes.

## Conventions

These exist because the two servers have to agree byte for byte in places.

**Database.** Use `postgres::pool()` and the `params!` macro. Every parameter
is bound as text and typed by the statement, exactly as the Bun pool does, so
SQL can be carried over unchanged. Rows come back as `postgres::Row` with each
column already in its API shape: BIGINT and NUMERIC as numbers, `timestamptz`
as an ISO string in milliseconds, JSONB as `serde_json::Value`.

```rust
let result = pool()
    .query("SELECT mail_id, read FROM mails WHERE user_id = $1", &params![user_id])
    .await?;
for row in &result.rows {
    let (id, read) = (row.text("mail_id"), row.bool("read"));
}
```

Bind a JSONB value with `Param::json(&value)` and a list for `= ANY($1)` with
`Param::array(&items)`. For a transaction or an advisory lock, check out one
connection with `pool().connect()`.

**JSON.** `serde_json` is built with `preserve_order`. Response fields are
written in the order the Bun server writes them: the `ETag` is a hash of the
body.

**Strings.** A JavaScript `length` or `slice` counts UTF-16 code units. Where
a limit is observable, use `js::utf16_len` and `js::utf16_slice`, not
`str::len`.

**Regular expressions.** The `regex` crate is Unicode-aware where JavaScript
is not: `\d`, `\w` and `\b` are ASCII-only in JavaScript (without the `u`
flag), and `\s` is a fixed list. Write `[0-9]`, `[A-Za-z0-9_]` and
`(?-u:\b)`, or disable Unicode for the group. `regex` has no look-around or
back-references; use `fancy-regex` for a pattern that needs them. Compile a
pattern once, in a `OnceLock` or `LazyLock`.

**Dates.** `js::date_parse`, `js::iso_string` and `js::utc_string` reproduce
`Date.parse`, `toISOString()` and `toUTCString()`.

**Errors.** Fallible functions return `anyhow::Result`. A route answers a
client mistake with a `failed` body; an `Err` becomes the generic 500.

**Logging and alarms.** `logger::info("message", json!({ "key": value }))`,
`logger::error_with("message", json!({}), &error)`, and
`alarm::spawn_alarm(title, detail)` for a Discord alarm nobody waits on.

**Environment.** Read settings through `env::var` / `env::non_empty` when they
are needed, not once at start.

## Known differences from the Bun server

Everything the black-box suite pins is identical. These differences are
deliberate or unavoidable, and no test pins them:

- **TLS.** The mail listeners use rustls (TLS 1.2 and 1.3). It has no CBC
  cipher suites, so a mail server that offers only AES-CBC at TLS 1.2 cannot
  connect, where Bun's OpenSSL accepts it. The certificate is read at every
  handshake rather than once at boot, so a renewed certificate is served
  without a restart.
- **HTTP parsing.** A `#` inside a request target is dropped by the HTTP
  library before the server sees it. Answers given by the parser itself
  differ in their headers: the 400 for an HTTP/1.1 request without `Host`, a
  431 for oversized headers, and an unknown method containing digits or `_`
  (Bun answers 400, Rust closes the connection).
- **Passwords.** Only bcrypt digests are verified. Bun would also verify an
  argon2 digest, which nothing in the app ever writes.
- **Ordering where Bun's is a race.** A FETCH over several comma-separated
  ranges answers in range order; Bun's order depends on which concurrent read
  finishes first.
- **Deep nesting.** SEARCH and UID nesting are bounded by fixed limits
  (22,000 and 27,000 levels) instead of the JavaScript stack, and JSON bodies
  are kept to 4,096 levels. Inside the protocols' own size limits both
  servers accept the same input.
- **Wire chunking.** Base64 bodies are written in different chunk sizes; the
  octets are the same.
- **Timing and logs.** An IMAP client that disconnects mid-command is noticed
  once the command finishes. Some log lines differ in wording (socket and TLS
  errors, the IMAP per-command diagnostic has no heap fields); alarm titles
  and the warn-versus-page split are the same.
- **Time zone.** Dates without an offset are read as UTC, the zone the server
  runs in.
